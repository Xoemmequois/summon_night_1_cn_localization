CM2000.DAT 战斗准备界面 (battle_prepare_ui) 内存结构分析
========================================================

对应 Ghidra 函数链 (SLPS_025.42):
  主循环 → FUN_80022F2C(VM2驱动) → UpdateVM2(0x800230CC) → SCP字节码
  装载入口: FUN_8004FFFC / VM2 opcode处理器(0x800427DC)
    → FUN_800428D4 → FUN_80042918(UI资源装载器)
  上传链:   FUN_80029944(层装载) → FUN_8002E8F0(CLUT上传)
                            → FUN_80029B08(PIX LoadImage)
  块表循环/FUN_80029944 内部, 精灵表基址 0x800BBB20 + id*0x400

一、容器定位
----------
- DAT索引: subcontent id = 0x10
- 文件偏移: 0x16C800 (sector 0x2D9 起, 长 162 sectors = 0x51000 字节)
- 运行时整体读入 RAM 0x80110000 (即 blob偏移 + 0x80110000 = RAM地址;
  blob偏移 + 0x16C800 = 文件偏移)
- 注: 用户所称 "0x2DF sector" 实为该 subcontent 内部数据所在扇区,
  容器起点是 sector 0x2D9。

二、顶层结构 (flat 表)
--------------------
+0x0000  u16   flat_count = 14
+0x0004  u32   flat_offsets[14]  (24位有效, &0xFFFFFF, 0=空)
  flat[1]  = 0x40     size 0x1AB2C  ← 战斗准备UI包 (本文重点)
  flat[3]  = 0x1AB6C
  flat[5]  = 0x21598
  flat[7]  = 0x47734
  flat[9]  = 0x477D8   (16×1 CLUT + 4w×256h 4bpp窄条, 疑似字体/光标条)
  flat[11] = 0x4826C

三、flat[1] 战斗准备UI包 (+0x40 .. +0x1AB6B)
------------------------------------------
+0x0040  二级目录: u32 count=8; u32 off[8]
         = {0, 0x28, 0, 0xB20, 0x8F24, 0, 0x11540, 0x19758}
+0x0064  u32 0xFF01AB2C (包结束标记: 0xFF标志|包长0x1AB2C)
+0x0068  "SCP\0" 魔数 + u32 长度0xAF0 + VM2字节码(约0xAF0字节)
         - 该脚本经 FUN_80022B98 注册为 VM2 state#1,
           回调 = FUN_800432C4 (巨型switch, case 0x13~0x3B 为UI事件API)
         - 每帧由 UpdateVM2 执行, 驱动整个界面的动态逻辑
         - 脚本尾部 0xFFFF 终止符约在 +0xB58
+0x0B60  TIM#1 层描述头 (前景层), 结构相对 0xB60:
         { u32 flags=0; u32 clut_off=16; u32 pix_off=532; u32 tiles_off=0x8218 }
  +0x0B70  CLUT: 16×16 RGB555 (16套调色板 × 16色, 512字节)
  +0x0D74  PIX头: 64 words × 256 → 256×256 4bpp
  +0x0D78  像素数据 (=RAM 0x80110D78, 即 LoadImage src,
           VRAM rect=(320,256,64,256))
+0x8D78  TIM#1 静态tile表: u32 count=61; 每项8字节:
         { u16 dst槽位; s16 调色板号; u8 x; u8 y; u8 w; u8 h }
         - 渲染模型: 屏幕矩形==纹理采样矩形(src==dst同坐标),
           pal 选择本层16套调色板之一, 索引0透明
         - 写入精灵表 0x800BBB20 + id*0x400 + dst*8
           = {tpage, clut_pos, x, y, w, h}
+0x8F64  TIM#2 层描述头 (背景层), 结构与TIM#1完全相同
         {0, 16, 532, 0x8218}
  +0x8F74  CLUT: 16×16
  +0x9174  PIX头, +0x9178 像素数据 256×256 4bpp
+0x1117C TIM#2 静态tile表: count=128, 条目格式同上
+0x1A984 动态部件源矩形表: 122项 × 4字节裸 (x,y,w,h)
  +0x1A9A8  (72,104,48,16)  ← UI文字区域(动态文本框源)
  +0x1A9B0  (72,104,24,16)  ← 同区域半宽变体(伸缩拼接用)
  - 由 VM2 脚本运行时按索引取矩形, 从TIM#1图集裁剪后自由摆放,
    目标坐标由脚本给出 (区别于静态tile的同坐标自放置)
  - 表尾恰好对齐 flat[1] 包边界 (+0x1AB6C)
+0x1AB6C flat[2] 起始 (下一flat条目)

四、资源槽系统 (FUN_80033ED4 / F8C / FE4)
---------------------------------------
注册表位于 0x800C1858, 每项12字节:
  +0x00 u16 在用标志(0xFFFF=空闲)
  +0x04 u32 资源基址指针
  +0x08 u32 槽偏移表指针 (=基址+4)
槽偏移表: u32 offsets[], 24位有效, 大小=下一个非零偏移-本偏移。
FUN_80042918 使用槽位:
  slot 1        : VM2脚本 → memcpy到0x80180000 → FUN_80022B98注册
  slot 3/4/6    : 图像块 → FUN_800298D8(id,x,y) 分块上传
  slot 7        : 布局blob → memcpy → FUN_800289AC 注册精灵组
  slot 职业类型+1: 角色头像块 → FUN_80029944(5,0x15,0x1F,0x50,200,…)
FUN_80029944 参数结构 (ushort* param_6):
  +0x00 u32 页标志(低字节<<8 | param_2 构成VRAM定位字)
  +0x04 u32 CLUT块偏移 → FUN_8002E8F0 上传(双写0x801C0000区)
  +0x08 u32 PIX块偏移  → FUN_80029B08 LoadImage
  +0x0C u32 tile表偏移 → 循环写精灵表 (仅 id<8 时执行)
FUN_80029B08 VRAM坐标计算:
  x = ((param_2&0xFF) >> (4bpp?2:1)) + (param_1&0xF)*0x40
  y =  (param_3&0xFF) + (param_1&0x10)*0x10

五、渲染合成模型
--------------
完整界面 = 背景层(TIM#2, 128 tiles) + 前景层(TIM#1, 61 tiles)
         + VM2脚本动态部件(122个源矩形裁剪, 含文字框)
静态tile与动态矩形合计覆盖两层图集全部有效像素。
每层独立 CLUT(16套调色板), tile 的 pal 字段按层内索引选择。
